## What this study produces

Four diagnostic IBU+BBB releases whose highest pT_h gen/reco bin edge is
extended from 8 GeV to (a) 15 GeV (`ptmax15`), (b) 25 GeV (`ptmax25`),
(c) 50 GeV (`ptmax50`), and (d) an inf-equivalent sentinel edge of 1000 GeV
(`ptmaxinf`), everything else identical to the central 8-GeV chain. Per
variant: 73 RAPGAP31 response shards → merged response + binmap → release →
validation. Then one four-variant comparison against the current central
8-GeV release. Highest-pT row = gen pT bin index 4 (pT_h in [4, last_edge)),
49 bins/charge = 98 rows per release.

Physics conventions (unchanged by the scan): photon-axis pT_h/z, 7 cells
(S0_x0..S3_x0) x z edges [0,0.05,0.1,0.2,0.3,0.5,0.7,1.0], gen pT edges
[0,0.5,1,2,4,**last**], reco pT edges [0,0.25,0.5,0.75,1,1.5,2,3,4,6,
**last**], NB_G=245, NB_R=490/charge, TH2 (491,246)/charge, data vector
980 (charge-major, 0..489 = h+, 490..979 = h-), 2 reco children/gen bin.
Prior method rule (ADOPTED 2026-10-07): coherent body+miss truth marginal
from the VARIANT merged `h_R_<charge>_rapgap`; IBU k=4; RAPGAP31 response;
LUMI = 351000.0 nb^-1. Never a plain w_gen-only prior.

## Why the canonical snapshot scripts could not be reused as-is

The finalcandidate v4 chain builders hard-import `binning_v3` from their
own directory (`sys.path.insert(0, _HERE)`) with no env/CLI override, and
the pT edges are module-level constants. Changing the last edge therefore
requires either editing canonical files (forbidden) or a fork with a
selectable binning module. The study forks carry a REQUIRED
`PTMAX_SCAN_BINNING` env selector (no default; every builder fails loudly
when it is unset or invalid) so no job can silently run the wrong binning.
The release driver additionally hard-codes all release/merged/data paths
at module level, so it needed a path fork pointing into the study tree.
Forks were generated by exact-match transformation of their bases
(shard builder: the rebuild study's `build_coherent_prior_response_shard.py`
with `--weights-json unity` = central-equivalent; data vector:
`build_data_vector_v4.py`; merge: `merge_migration_per_charge_v4.py`;
release: `run_bbb_ibu_release_coherentprior.py`), so the physics code is
verbatim-identical to the proven chain.

## Comparison content and interpretation

- Last-bin (pT_idx==4, 49 bins/charge) `cross_section_nb` per bin;
  relative change 8→15 and 8→inf per charge: median, max, min signed,
  max |rel|.
- Density-normalized last-bin xs/dpT. For ptmaxinf the 1000 GeV sentinel
  makes the density ill-defined: the report carries BOTH the sentinel
  density (dpT = 996) and an effective-support density (dpT = 96, from
  the sidistree lab-P cap of 100 GeV which bounds the CM pT_h support),
  with an explicit caveat — compare densities only where the support is
  comparable.
- Lower-pT sanity (pT_idx < 4, 392 rows/charge): max relative deviation
  vs central, quantified. Gate = PHYSICAL tolerance 1e-3 rel, not
  bit-identity: IBU couples every gen bin to the last reco bin (response
  tail entries + changed data count + changed f_i), and BBB aggregates
  the 2 reco children with acceptance shifts from ex-fake gen-pT-8-15
  partners, so pT<4 cross sections move at O(absorbed fraction) — tiny
  but nonzero. The exactness gates live at merged-response level (G3a).
  The count of bit-exact bins is reported for information.
- 15-vs-inf cross-check on the last-bin rows.
- cross_section_nb values are PROVISIONAL diagnostics (raw, no
  bg-subtraction, no C_rad, not Born-level): draw the scan conclusion
  from RELATIVE changes only; do not quote absolutes.

## Failure handling

- **Stage 2 counts wrong / zero-size shards**: do not merge; inspect
  `$CONDOR/logs/${V}_shards.*.err` for the failed jobs; resubmit only
  the missing shard jobs (`condor_submit` is idempotent per shard list
  line — verify the output file exists and is non-empty before skipping).
- **G1-meta-shards != 73**: the merge ran over a partial glob; delete the
  merged outputs and redo Stage 3 after Stage 2 truly passes.
- **G3a FAIL with tiny (~1e-16) deviations**: would indicate an
  accumulation-order drift between the merge fork and the rebuild merge
  (not expected; equivalence verified 2026-10-08). Do NOT relax the gate
  on the spot — escalate to the analysis owner with the failing cells.
- **G4b FAIL**: the merge consumed a stale/mispointed data JSON; rerun
  Stage 3 with the wrapper as-is (paths are hard-coded correctly).
- **Release job missing status.json**: read
  `logs/run_release_ptmax_${V}.log` in the release dir; the driver fails
  loudly on env or input problems.
- **Any gate FAIL**: stop that variant's pipeline; the other variant may
  proceed independently. Nothing is promoted; the study is diagnostic.
