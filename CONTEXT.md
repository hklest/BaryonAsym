3 h runtime) to bypass group quota limits and access the full NAF pool.

quota and may queue longer. Prefer splitting work into standard-sized
chunks over requesting large resources.

- **TMD fiducial requirement — NO detector-geometry cuts at gen level (added 2026-05-28).** For any TMD-grade unfolded cross-section, the unfolded result MUST be a function of the physics observables `(Q², x, z, pT_h)` only — NOT of detector geometry. Concretely: do NOT impose `|GenEta| < 1.6` or `GenPt > 0.15` (or any similar detector-acceptance cut) on the gen denominator. The BBB acceptance ε MUST absorb the geometric inefficiency. The low-Q² SIDIS d1 baseline inherited such a cut via `make_gen_analysis_fid_mask` and propagated it through every cascade up to v4_empz45 and v1 of empz45_xf0; the v2 cascade removed it via a `--no-gen-fid-cut` flag and the cross-section initially rose 3.7× to 783.7 nb. NOTE: v2's 783.7 nb is now known to be inflated by a separate hemisphere-mismatch bug (v2 imposed `xF_H1>0` on reco but missed `xFGen<0` on gen); v3 fixed that and σ_total is expected to drop back to ~400 nb. The TMD no-gen-cut requirement itself remains correct and frozen. Any new SIDIS analysis or cascade must default to no gen-track cut. See `H1/sidis_lowQ2/docs/empz45_xf0_v2_TMD_fiducial_2026-05-28.md` (v2, no gen cut but hemisphere-mismatched) and `H1/sidis_lowQ2/context-handoff.md` § "2026-05-28 (continuation) — v3 acceptance cascade" (TMD-correct, hemisphere-matched).
- **d4 stability definition is ~2× over-estimated (added 2026-05-28).** Per the prior PURITY-vs-STABILITY label-swap audit, the field named `P_4D` in `d4_merge_and_analyse.py` is stability (N_correct / N_gen). However the d4 producer derives `N_gen` from records that REQUIRE a reco match, so it actually computes `N_correct / N_gen_matched` instead of the TRUE stability `N_correct / N_gen_TOTAL`. The denominator excludes the ~50% of gen tracks with no reco partner, so the reported value is ~2× the true value. Corrected computation on the v2 cascade (`H1/sidis_lowQ2/data/binning_redesign_2026-05-24/empz45_xf0_v2/scheme_A_4d_purity_AND_stability_CORRECTED_empz45_xf0_v2.json`, produced by `compute_corrected_stability_v2.py`) gives true stability median **0.326** vs the broken d4 median **0.589**. Purity (true field `S_4D`, `N_correct / N_reco_total`) is reco-only and unaffected. The d4 producer is NOT yet patched — future SIDIS analyses should use the corrected JSON, or rebuild stability with `N_gen_TOTAL` taken from `ChargedTotGen` directly OR from d1's `rad_gen_QxXzPt_*` arrays (full gen, no reco-match requirement). BBB acceptance ε is independent of this definition and unaffected.
- **Use yield-weighted aggregate, not per-cell median, when reporting acceptance and similar figures of merit (added 2026-05-28).** A per-cell median is dominated by populated central cells and can mask the impact of low-acceptance forward cells on integrated quantities. When summarizing acceptance changes (or any cell-level metric whose downstream consumer is a yield integral) use the yield-weighted aggregate `sum(N_data) / sum(N_corrected)`. Example: removing the low-Q² SIDIS gen-track cut shifted per-cell median acceptance only 0.83 → 0.68 (−18%), but the yield-weighted acceptance shifted 0.829 → 0.257 (factor 3.2 drop) — exactly matching the 3.22× corrected-yield rise. The median figure made the 3.7× cross-section change look inconsistent; the yield-weighted figure makes it transparent.
- **Reco/gen hemisphere cuts MUST be matched (added 2026-05-28, low-Q² SIDIS v3 root cause).** When a hemisphere selection is applied on the reco numerator it MUST be applied with an equivalent cut on the gen denominator, recognizing that branch sign conventions may differ. In the low-Q² SIDIS analysis, the reco helper `compute_sidis_hcm.py` returns `xF_H1` in literature convention (`xF_H1 > 0` = current hemisphere) while the gen branch `xFGen` on `ChargedTotGen` is in H1 OO convention (`xFGen < 0` = current hemisphere). The two cuts that select the SAME physical hemisphere have OPPOSITE inequality directions. The v2 cascade imposed `xF_H1 > 0` on reco but did NOT impose `xFGen < 0` on gen, so the gen denominator counted both hemispheres → ε artificially small by ~factor 2 → σ artificially large by ~factor 2; the 12% v2 h+/h- asymmetry was backward-hem target-remnant contamination, not u-quark dominance. v3 fixed this by adding `xFGen < 0` via the existing `_xf_track_mask_h1` helper.
- **BBB MC-model bias in absolute cross-sections (revised 2026-05-29 continuation 2; supersedes earlier "BBB ε formula bug" entry).** The standard textbook BBB formula ε = N_reco/N_gen (per Schmitt 2016 Eq. 11, Cowan §11.4, COMPASS Eq. 5; as used in H1 EPJC 81 (2021) 212, HERMES PRD 87 (2013) 074029) is the well-known biased estimator in the presence of bin migration. When MC shape differs from data shape in regimes with moderate purity (~0.5-0.7), BBB carries a documented MC-model bias of up to ~10-20% per cell per Schmitt 2016 §4.1. **The earlier framing of this as a code bug in the low-Q² SIDIS BBB acceptance script is RETRACTED** — BBB v3 implements the textbook formula correctly; the bias is intrinsic to the BBB methodology, not a coding error. In the low-Q² SIDIS analysis the previously reported 19% TUnfold/BBB σ gap is a composite of (1) BBB MC-model methodology bias ~1-2% integrated per closure test (per-cell pattern 5-24% mostly cancels in integral), (2) C_rad provenance v2-baked → v3p3 ~2.5%, (3) diagonal-ε vs rate-ratio-ε per-cell effect ~5%, (4) v3p3 prior_gen swap + eSigma method consistency fixes ~5-10% (correctly applied in v3p3). **Canonical fix:** use regularized matrix inversion (TUnfold or IBU), which is robust to MC-model shape differences (~few % residual model dependence). **Cross-analysis impact:** the Schmitt-style BBB MC-model bias applies anywhere BBB is used with MC shapes differing from data shapes in moderate-purity regimes. Other H1 BaryonAsym analyses using BBB (proton, V0/Lambda, Xi, exclu_phi) should audit their BBB usage and either provide an unfolded cross-check or carry the documented bias as a systematic. See `H1/sidis_lowQ2/docs/bbb_mc_model_bias_2026-05-29.md` (renamed from `bbb_eps_formula_bug_2026-05-29.md` with prominent correction box at top).
- **Noiseless `R · truth` is NOT a valid closure test in HEP unfolding (added 2026-05-29 continuation 3).** A closure test must construct pseudo-data at reco level with Poisson fluctuations (`N_pseudo_reco ~ Poisson(λ = R · truth)`), unfold N ≥ 100 pseudo-experiments with the same response and regularization used on data, and report per-cell bias, variance, and coverage. Deterministic forward projection `pseudo = R.sum(axis=1)` measures only matrix-inversion arithmetic and cannot detect finite-statistics bias, variance under-estimation, coverage failure, or prior dependence under realistic fluctuations. Reference: Schmitt 2016 (arXiv:1611.01927) §6; Cowan, *Statistical Data Analysis* §11. The low-Q² SIDIS v3p3 closure-test script (`scripts/unfolding/closure_tunfold_vs_bbb.py` Test A lines 213–216, Test C lines 329–333) made this mistake and produced a misleading 0.022% integrated closure result; three independent critics (h1-analysis-critic, implementation-critic, research-critic) returned FATAL on 2026-05-29 continuation 3. The systematic budget was RE-OPENED. **Applies to any analysis that unfolds:** Lambda 4D anchor30 pipeline, SIDIS low-Q², SIDIS high-Q², and any future migration of proton or Xi to unfolding methods. Audit any "closure" or "self-consistency" check that does not explicitly invoke Poisson fluctuations at reco level.
- **Per-cell systematic broadcast from a parent integrated value hides fine-bin failures (added 2026-05-29 continuation 3).** When a systematic source is computed at one binning level (e.g. per-(Q², x, charge) parent cell) and then assigned to a finer binning (e.g. per-(Q², x, z, pT_h, charge) child cell) by broadcast, document the broadcast explicitly and audit it: check whether the finer bins carry variance that the parent hides. The low-Q² SIDIS v3p3 S7 closure systematic (`compute_systematics_unfold_v3p3.py` lines 226–246 build parent table, line 461 broadcasts to children) made this mistake: multiple distinct (iz, ipT) cells share `delta_S7_closure_rel = 0.016861706652403982` regardless of (iz, ipT), and 162/761 fine pT_h bins that fail >20% closure are all assigned the parent's ~1.4% systematic — under-stating per-cell uncertainty by 5–10× in worst regions (high-z iz = 5 and edge pT_h ipT = 0/7). A_h precision is especially fragile because charge-asymmetric per-cell migrations get hidden by the broadcast. Multiplicities get false precision from numerator-broadcast vs denominator-per-(Q²,x) mismatch.
- **`ChargedTotGen` has built-in species + GTR + Mother2 filters at fill time (added 2026-05-28).** In the low-Q² SIDIS v5g builder (`ChargedSidisTreeBuilderLowQ2.C`), `ChargedTotGen` is populated by ONE entry per (event, gen π/K/p) with three deliberate fill-time filters: species (L956, `isChargedHadron(GenPDG)` → only `|PDG| ∈ {211, 321, 2212}`), GTR-only (L974, `IsGtr() == true` → no STR/GEANT3 secondaries), and no second mother (L979, `Mother2 == -1` → no combinatorial reinteractions). Direct PDG inspection on a v5g RAPGAP31 Rad file confirms 79.20% π / 9.92% K / 10.88% p / 0.000% all else; 100.0% `IsGtr=1`. Downstream analyses should NOT assume additional species or quality filters are needed — and an analysis-level `IsGtr==1` mask is a no-op but harmless. `IsGtr` is pure-truth (defined as `fStrIdx == -1` in `H1PartMC.C:193-197`, NO reco dependence). The matching pool on the reco side admits STR by design (for V0 flagging) — that admission does NOT propagate to `ChargedTotGen`.
- **H1EventList Add-vs-Merge applies to evls builds, not just reco merge (added 2026-05-30).** When TreeBuilder is run in `--stage evls` mode against multi-file HAT inputs, it may produce a ROOT file with N separate `H1EventList` backup cycles instead of one unified `EvlList`. Downstream `f->Get("EvlList")` then returns only the LAST cycle, suppressing event counts by ~N×. Symptom: MC reco production uniformly N× undersized across all trees per input catalog. In the V0 v3.2 reproduction, 128 MC evls files each had 39 separate `H1EventList` cycles, causing all 256 Phase 3 (MC reco) jobs to produce outputs 252× undersized (16k instead of 830k events per file). Fix: run `H1BaryonAsym/scripts/fix_evls/fix_evls_merge.C` macro (proven on V0 v5 and v3.2) over each evls file before consuming. Validator must check `H1EventList::GetN()` on the actual list object, NOT just key presence or `EvlTree` num_entries (which reflects only the last cycle). Audit any pipeline that runs `--stage evls`. See `H1/lambda/docs/v3p2_mc_reco_shortfall_diagnosis.md` for full forensics.
- **`LambdaRegGen`/`LambdaBarGen` are TWO different trees with the same name in `TreeBuilder_v3.C` (added 2026-05-30).** The matched-truth pairs version (one entry per matched candidate, schema has reco-side + gen-side branches) is at TreeBuilder line 913 inside `isMCMode`. The standalone-gen version (one entry per gen V0, gen-only schema) is at line 2707 inside gen-only mode. K0s does NOT collide — matched-truth is `KaonTotGen` and standalone-gen is `KaonRegGen`. Acceptance / efficiency scripts must explicitly know which file type they are opening; mixing them silently produces 10²–10³× normalization mismatches. Any V0 (Lambda/K0s) analysis that uses both matched-truth and standalone-gen trees MUST distinguish file type before reading. See `H1/lambda/docs/v3p2_T6_miss_routing_canonical_research.md` §5.
- **v3 fingerprint is `inFiducial`/`genInFiducial` + `GenEmpz≥45`, NOT eΣ branches alone (added 2026-05-30).** Older H1 V0 TreeBuilder vintages also wrote `Q2es`/`Yes`/`Xes` and `Q2esgen`/`Yesgen`/`Xesgen` branches — these alone are NOT proof a file came from v3+ (eΣ-cut + Empz≥45 era). The actual v3+ fingerprint is: standalone gen files have `inFiducial` branch; MC reco matched-truth-gen trees have `genInFiducial` branch; under either fiducial flag == 1, `GenEmpz ≥ 45.0` floor is enforced; reco-side surviving events have `Q2es ∈ [5, 100]` and `Yes ∈ [0.1, 0.6]` STRICTLY (zero violators), with `Q2s`/`Ys` extending OUTSIDE those windows as positive evidence the cut variable changed from Σ to eΣ. Validators that only check eΣ-branch presence will pass stale pre-v3 files. See `H1/lambda/docs/v3_gen_provenance_check.md` for the corrected fingerprint.
- **Compound boolean Condor constraints can mis-parse (added 2026-05-30).** Queries like `condor_q -constraint 'ClusterId>=A && ClusterId<=B && (ClusterId<C || ClusterId>D)'` may have parentheses dropped by the schedd parser in some versions, collapsing to `(A && B && C) || D` and matching unrelated clusters. Workaround for all monitoring and kill operations: use awk numeric filters on `condor_q -af ClusterId ProcId JobStatus` output instead of compound boolean constraints. Pattern: `condor_q klesthen -af ClusterId ProcId JobStatus | awk '$1 == CLUSTER {s[$3]++} END {for (k in s) print k, s[k]}'`. Verified leak in V0 v3.2 Phase 2 monitoring: compound constraint counted unrelated cluster 3547828 in addition to the target range; awk-based monitors across 5+ subsequent deployments had no issues.
- **Single-stage smokes against pre-built upstream products cannot validate upstream code changes (added 2026-05-30).** A common failure mode in the V0 v3.2 session was running `--stage lambda` (downstream) against pre-built EventLists from a prior production to validate a `--stage evls` (upstream) code change. The downstream stage inherits the upstream filter unchanged, so the new upstream cut is never exercised. To validate a stage_evls change, run stage_evls FRESH from raw DST and then stage_lambda against THAT fresh EventList. The same pattern holds for any multi-stage pipeline: the smoke must exercise the changed stage from its actual entry point. The lambda-only smoke approach masked the Σ-vs-eΣ cut bug for several dispatch rounds in the v3.2 session. See `H1/lambda/docs/v3p1_fullchain_smoke_verification.md`.

- **TreeBuilder rad-MC gen trees can contain asymmetric secondary feed-down; mother-PDG allowlist must be applied at C_rad-compute time (added 2026-06-01).** In the v3.2 H1 V0 production, `rapgap31_rad/LambdaRegGen` includes ~22% secondary Λ from K-meson (PDG 130, -321) and Ξ⁻ (3312) feed-down via GHEISHA detector-material interactions. The nonrad gen sample is clean (no such feed-down) and the matched-truth-gen MC reco trees are nearly symmetric Λ/Λ̄ via `LambdaIsStr`. Because K-meson → Λ+X happens in material but K-meson → Λ̄+X is suppressed, this contamination is asymmetric, biasing C_rad_Λ vs C_rad_Λ̄ by 20-25% in central cells and propagating into a 30% fake σ_Λ/σ_Λ̄ asymmetry. **Fix**: apply the same mother-PDG allowlist (rejecting K-meson, Ξ etc. for Λ contributors) used by the acceptance script at C_rad-compute time. The V0 acceptance script already does this; the C_rad script did not. Audit any C_rad computation against gen trees to ensure the mother-PDG filter is applied. See `H1/lambda/context-handoff.md` Section 23 finding #6 for full forensics. Also relevant: `IsFromSecondary` reco branch is geometric (high-DCA daughters), NOT truth, and fires on ~92% of K0s daughters; do NOT use it as a secondary-veto.
- **Truth selection must be SYMMETRIC across acceptance numerator, denominator, and C_rad (added 2026-08-28; root cause FIXED same day).** A V0 3D chain applied the mother-PDG allowlist at C_rad and a `ParticleSource` cut at the gen denominator, but left the matched-reco numerator on `MatchResult==1` alone. Material-interaction Λ that angular-match a true gen Λ then leak into the numerator while the denominator is restricted, locking in a one-sided bias (HERA target material is matter, so material V0 production is strongly Λ-favoured; PS=4 is 1.01% of Λ vs 0.0091% of Λ̄, a 122× asymmetry; the allowlist rejects 98.8% of Λ PS=4). Result was Λ/Λ̄ = 1.231 vs the Anchor30 1.078 reference. **Fix verified: applying the identical allowlist + source cut to the numerator moved the ratio to 1.0529 ± 0.0467.** Note the Anchor30 source definition is `ParticleSource ∈ {0,1,2,3,6}` rejecting `{4,5}` (`TreeBuilder_v3.C:2934-2942`) plus the allowlist — **`0-3` alone is NOT the Anchor30 definition**, and a chain whose C_rad still uses `0-3` while its acceptance uses `{0,1,2,3,6}` is internally inconsistent. Separately, `V0_DECAY_RADIUS_MIN=5.0`/`MAX=20.0` in `PhysicsConstants.h` are **defined but never applied in any V0 chain**; only the upstream H1FindLambda ~1.5 cm floor exists. Finally, MC truth filtering does NOT remove material Λ from the fitted DATA mass peak and can amplify it by 1/ε; that needs an explicit MC-derived PS=4 per-cell subtraction. See `H1/lambda/context-handoff.md` §28.
- **A paired ratio and its asymmetry must share ONE covariance model (added 2026-08-28).** In the V0 3D chain, `build_xsec_xqz3d.py` propagated the common per-cell combined-C_rad covariance into the Λ/Λ̄ ratio (±0.0467) while `compute_asymmetry_xqz3d.py` treated the two corrected species cross-sections as statistically independent (±0.0056 on A). Whenever a species-independent or otherwise shared correction (combined C_rad, shared acceptance model, common luminosity) enters both legs of a ratio or asymmetry, build one paired-cell covariance model and derive BOTH observables from it. Applies to any H1 analysis quoting particle/antiparticle ratios or asymmetries.

- **TUnfold algorithm REQUIRES n_reco ≥ n_gen (added 2026-05-31).** Schmitt 2012 (arXiv:1205.6201v4) §1 immediately after eq. 2 and restated in §2.1: "the data y_i have to be measured in finer bins than are extracted by the unfolding procedure. This condition n ≥ m..." where n = reco bins (dim of y) and m = gen bins (dim of x). Inverted ratios (gen finer than reco) produce a rank-deficient response matrix; the regularizer (not the data) drives the per-bin solution; off-diagonal |ρ| approaches 1.0 across all τ; closure tests fail catastrophically (per-bin bias −30% to −600% at every τ tested in low-Q² SIDIS v1). The conventional "gen 2-4× finer than reco" folklore from some unfolding contexts is INCOMPATIBLE with TUnfold's algorithm and must not be applied. Verify n ≥ m before any TUnfold deployment. Other H1 analyses using TUnfold (Lambda 4D anchor30, future proton/Xi if they migrate from BBB to unfolding) should audit their reco/gen bin counts. **Other TUnfold paper recommendations to consider** (Schmitt 2012, low-priority but useful): use `kDensityModeBinWidth` not `kDensityModeNone` for non-uniform bin widths (§7.2.1 eq. 29-30); use `TUnfoldBinning` class not flat TH2D for multi-dim structured binning (§8); subtract residual reco background via `SubtractBackground` not a synthetic "fake column" (§5 eq. 26-27); the Britzger "miss row" Encoding B IS native and correct (§3 eq. 19-20); `kEConstraintArea` is recommended for Poisson data; `kRegModeCurvature` is allowed but interacts with non-uniform widths so must be paired with proper density mode. Cite Schmitt 2012 sections explicitly when defending unfolding choices. See `H1/sidis_lowQ2/docs/research/tunfold_paper_optimization_2026-05-31.md` for the full paper-cited recommendation set.

## SIDIS pT_h / phi_h must be CM-frame (2026-05-24)

The H1OO ChargedTot tree stores raw lab-frame 4-vectors only; downstream code must boost to the `\gamma*+p` CM frame (`W = q + P`, using per-event `BeamProtP`) before computing `pT_h` or `phi_h`. Lab-frame `|p × q̂|` or Trento cross products give wrong answers at HERA asymmetric kinematics. Canonical extractor: `sidis_highQ2/scripts/extract_pertrack_v5g_fixedFrame_v3.py`, which supersedes v2 and adds corrected CM-frame `phi_h` alongside the retained audit column `phi_h_old`. The `phi_h` correction shifts the full-sample weighted moments by about an order of magnitude: `⟨cos φ_h⟩` moved from about `-0.67` (lab) to `-0.09` (CM), and `⟨cos 2φ_h⟩` from about `+0.37` to `+0.03`. All pre-2026-05-24 v5f and early v5g `pT_h`-binned and `phi_h`-binned results are in the wrong frame.
